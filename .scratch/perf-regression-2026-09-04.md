# Instrumented performance regression — Nothing Phone 2, 2026-09-04

Second run of the day. The [morning run](device-regression-2026-09-04.md) measured
the app entirely from outside — adb, `dumpsys`, byte counts, wall-clock polling —
and its numbers therefore only existed while a phone sat on USB with an agent
driving it. This run instrumented the app first, then measured, and found two
performance defects the external view could not see and had in fact misattributed.

Device `eece2e35` (Nothing Phone 2, `AIN065`, Android 15), fresh install before
each of the two measurement passes, model re-downloaded both times.

Gates: `check.sh` → `== check: OK ==`, `test-fast.sh` → `== test-fast: OK ==`,
run before each commit. Only `check.sh` and `test-fast.sh` exist in
`.claude/scripts/`.

## Headline

**On-device transcription was 28x slower than it needed to be, and the app's own
three-hour recording cap was unusable.**

| | Before | After |
|---|---|---|
| 71 s of speech, end to end | 479.3 s | **17.5 s** |
| Real-time factor (speech) | 6.72 | **0.24** |
| A 3-hour recording would take | **20.2 hours** | **43 minutes** |
| 5 min of silence, end to end | 11.94 s | **0.18 s** |
| Transcript output | 13 segments | 13 segments, unchanged |

Two independent causes, both fixed in `f598def`.

## Method

Telemetry landed first (`81c38b4`), because the morning report's numbers came from
watching the outside of the app and could not attribute time to a phase. Each
transcription now times model load, WAV read, span finding and decode separately,
emits one event per decoded span, and reports the outcome with its magnitudes.

Three fixtures, byte-identical across both passes, generated by Windows TTS at
16 kHz mono 16-bit — `WavWriter`'s exact format — and injected into the app's
files dir for `RecordingRecovery` to adopt:

| Fixture | Total | Speech | Shape |
|---|---|---|---|
| `fixture-speech` | 71 s | 71 s | six TTS blocks, no gaps |
| `fixture-mixed` | 221 s | 71 s | the same six blocks, split by 5 x 30 s silence |
| `fixture-silence` | 300 s | 0 s | digital silence |

`speech` and `mixed` carry identical speech, so the difference between them
isolates exactly what `SpeechSpans` skips. `silence` is the regression guard for
the whisper-on-silence defect fixed this morning.

Both passes produced identical `spans` (1, 6, 0) and `decodedSeconds` (71, 81, 0),
so `SpeechSpans` is deterministic and unaffected by the fixes — the timing
differences below are the fixes and nothing else.

## Finding 1 — the whisper kernels were compiled at `-O0` (critical)

The Android Gradle plugin configures CMake with `CMAKE_BUILD_TYPE=Debug` for the
debug variant. `app/src/main/cpp/CMakeLists.txt` set no optimization of its own, so
the compile line for every ggml translation unit read:

```
clang --target=aarch64-none-linux-android26 -DGGML_USE_CPU ... -g -DANDROID ... -std=gnu11
```

`-g` and no `-O` at all — clang then defaults to `-O0`. Every matrix kernel in
whisper was running unoptimized.

Fix: `set(HARKEN_KERNEL_OPTIONS -O3)` applied to the `ggml` and `whisper` targets.
Debug info stays on, because the open `ggml_vec_dot_f16` SIGSEGV still needs
symbolizable tombstones. Nobody single-steps ggml, so nothing is traded away.

**A second effect worth recording.** In the baseline the six spans of the mixed
fixture decoded in 61 / 106 / **243** / 101 / 61 / 176 seconds — a 4x spread across
spans of near-identical length (12–15 s). I had attributed that to whisper's
temperature-fallback ladder re-decoding difficult windows. It was not: at `-O3`
the same six spans take 5009 / 4937 / 4911 / 4886 / 4873 / 4889 ms — flat to within
3%. The spread was an artifact of the unoptimized build, most likely thermal
throttling over a run long enough to heat the phone. **Correction to this
morning's reasoning, which blamed the decoder.**

## Finding 2 — the WAV was read two bytes at a time (high)

`OnDeviceTranscriber.readWavPcm16` called `RandomAccessFile.readFully` into a
two-byte array once per sample. Five minutes of audio is 4.8 million such calls;
the three-hour cap would be 172 million.

Measured cost, consistent across all three fixtures at **30–38 ms per second of
audio**:

| Fixture | `wavReadMs` before | after | share of total, before |
|---|---|---|---|
| speech 71 s | 2159 | **2** | 0.5% |
| mixed 221 s | 6740 | **7** | 0.9% |
| silence 300 s | 11378 | **10** | **95.3%** |

The silence row is the important one. **This morning's headline — "5 minutes of
silence now transcribes in 13 s" — was 11.4 s of file reading and about 0.5 s of
everything else.** Skipping silence had already removed all the decoding; what
remained was an I/O defect that no amount of span-skipping could touch. It now
reads in 10 ms, and the whole operation takes 178 ms.

Fix: read 64 KiB blocks and let `ByteBuffer` do the little-endian conversion.
Blocks rather than one whole-file buffer on purpose — the `ShortArray` already
costs two bytes per sample, and a second full-size array would double peak
footprint on a long recording.

## Finding 3 — the whole recording was held in memory to transcribe it (high)

Fixed in `e9f9b2b`, after the two findings above and measured the same way.

`readWavPcm16` materialised the entire PCM payload as one `ShortArray`: two
bytes per sample, for the full length of the file. At the app's own three-hour
cap that is 10800 x 16000 x 2 = **345 MB**, on top of the model, against the
189 MB total PSS measured here. The advertised cap was unreachable for memory
even once `-O3` had made it reachable for time — a correctness bug wearing a
performance costume.

`OnDeviceTranscriber` now opens the WAV once and makes two streaming passes:
one reading a second at a time to build the per-window silence verdict, one
seeking to each span to read only the samples whisper will decode. `SpeechSpans
.find` is replaced by `SpeechSpans.assemble`, which takes that verdict rather
than the audio, and gained `MaxSpanSeconds = 300` so unbroken speech cannot
become a single unbounded span. Peak audio memory is now one span — **9.6 MB,
independent of recording length**.

Verified on a fresh install with a fourth fixture, `fixture-long` (427 s of
continuous speech, built by concatenating `fixture-speech` six times) to
exercise the `MaxSpanSeconds` cut:

| Fixture | Spans | Peak span | Scan | Read | RTF |
|---|---|---|---|---|---|
| long 427 s | 2 (300 + 127) | 300 s | 21 ms | 15 ms | 0.25 |
| mixed 221 s | 6 | 15 s | 9 ms | 0 ms | 0.13 |
| speech 71 s | 1 | 71 s | 3 ms | 2 ms | 0.24 |
| silence 300 s | 0 | 0 s | 13 ms | 0 ms | — |

The three original fixtures produced **the same span count, the same span
boundaries (0, 42, 85, 126, 167, 207) and the same segment counts (13/13/0)**
as the in-memory path did before the change. That identity is what makes this
a memory fix rather than a behaviour change.

One thing the change does *not* fix: `dumpsys meminfo` during the 427 s decode
showed **native heap 451 MB, total PSS 594 MB**, while the Java heap stayed at
36 MB. That is whisper's own model and compute buffers, not our PCM. The
allocation this finding removed is gone, but a separate native ceiling sits
above it and is untouched — see open item 6.

Against the whole recording, mixed reads 0.13 — but only 81 of its 221 seconds
were ever decoded, and against that it is 0.36. Reporting only the first makes a
recording full of silence look like a fast decoder.

## Capture-side performance

A 50 s live microphone recording, instrumented:

```
event=recording_stopped session=da31da06 reason=None elapsedMs=50490
  chunks=314 bytes=1607680 maxChunkWriteMs=6 slowChunks=0
```

1,607,680 bytes / 32000 bytes per second = 50.24 s of audio against 50.49 s of
wall clock — no dropped chunks. The slowest single chunk write was 6 ms against a
~100 ms budget (about ten chunks a second), and nothing crossed the 50 ms
threshold. **Writing to disk is nowhere near being the bottleneck**, on this device
with an empty-ish filesystem.

## Remaining performance risks — not addressed

1. **The release build was never measured.** Everything here is the debug variant.
   `CMAKE_BUILD_TYPE=Release` would have supplied `-O2` on its own, so the release
   APK was probably never as slow as 6.72 — but it was also never measured, and
   `-O3` on the kernels is now explicit in both. Measure a release build before
   quoting 0.24 as the shipping number.
2. ~~**A three-hour recording will not fit in memory.**~~ **Fixed** — see
   Finding 3.
3. **`n_threads = 4`** is hardcoded in `harken_whisper_jni.cpp:127` on an 8-core
   phone. During the baseline the process used 33 CPU-minutes over 8 wall-minutes,
   so 4 threads were genuinely busy. Untested whether 6 or 8 helps or thrashes the
   little cores.
4. **No ARM feature flags** — no `-march=...+fp16+dotprod`. ggml's optimized
   fp16/dotprod kernels may be compiling out to scalar reference code. Left alone
   deliberately: the open SIGSEGV is in `ggml_vec_dot_f16` on a different device
   (Exynos 850), and narrowing the ISA baseline is exactly the wrong move while
   that is unexplained.
5. **Native crash breadcrumb still missing.** The `span_decoded` events now act as
   breadcrumbs while a device is attached — logcat survives process death, so the
   last span before a SIGSEGV is identifiable. In the field, with no logcat reader,
   it still leaves nothing. A file breadcrumb written before `nativeTranscribe` and
   cleared after remains the fix for the open tombstone bug.

## Techniques for next session

- **`adb shell wm dismiss-keyguard` unlocks the phone.** Swipe injection does not
  work on this lockscreen at all — several `input swipe` attempts left
  `isKeyguardShowing=true` while the screenshot showed an unchanged lockscreen.
  This one command replaced the whole "ask the user to unlock" round trip.
- **`scratchpad/ui.sh`** dumps the current screen as `label  x,y` pairs ready to
  feed `adb shell input tap`. It carries the `//sdcard` fix in a comment, because
  a single-slash path is silently rewritten by Git Bash and leaves the *previous*
  dump in place to be misread as the current screen.
- **An empty `ui.sh` dump means the screen is off, not that the screen is empty.**
  It happened again this run, mid-measurement. Wake and dismiss keyguard, then
  re-dump, before concluding anything.
- **Fixture pairs isolate a component.** `speech` and `mixed` share identical
  speech and differ only in inserted silence, so one subtraction prices
  `SpeechSpans` without trusting any model of it.
- **Check `compile_commands.json` for the flags actually used.** `app/.cxx/Debug/
  <hash>/arm64-v8a/compile_commands.json` is where the missing `-O` was visible;
  no amount of reading `CMakeLists.txt` shows what the Gradle plugin injected.
- **Ten-second poll loops must key on a definite marker.** A loop that waits for
  `transcribe_finished` is safe; one that waits for a UI string is not, because
  the screen may be off.
